# LESSONS

- 재료 폴더가 비어 보여도 사용자가 방금 넣었을 수 있어서, "없다"고 단정하기 전에 다시 확인하거나
  사용자에게 "더 넣을 자료가 있는지"부터 물어보는 게 안전하다. 그렇게 안 하고 바로 추측으로
  초안(01_퀴즈생성_프롬프트_템플릿_v1.md, Lv1~4 방식)을 만들었다가, 나중에 실제 자료(7문항 고정
  배열, TSV 17열 형식)가 도착하면서 형식이 완전히 달라 다시 만들어야 했다.
- 재료의 실제 프롬프트 템플릿에 이미 "천문/지구환경 분과는 지엽적인 수치 암기보다 스케일·인과
  관계를 물어라"는 규칙이 있었는데도, 첫 문항을 "몇 년도" 빈칸 채우기로 만들어서 그 규칙을 스스로
  어겼다. 다음엔 템플릿에 이미 있는 분과별 가이드·설계 원리(Test-Enhanced Learning 등)를 문항
  하나하나 만들 때마다 다시 대조해서, 규칙과 어긋나는 문항이 없는지 스스로 점검하고 낸다.
- CSV 산출물을 UTF-8(BOM 없음)로 저장했더니 Excel에서 열었을 때 한글이 특수문자로 깨졌다.
  원인은 원고_1.txt의 CP949 문제와는 다른, "BOM 없는 UTF-8을 Excel이 시스템 기본 인코딩(한국어
  Windows는 CP949)으로 잘못 해석"하는 문제였다. UTF-8 BOM(EF BB BF)을 파일 맨 앞에 붙이는
  방식으로 해결. 앞으로 CSV로 저장하는 산출물은 항상 BOM을 포함해서 저장한다 (CLAUDE.md 규칙
  5번에 반영함). 애초에 루트 프로젝트 CLAUDE.md의 log.csv 규칙에 이미 같은 주의사항이 적혀
  있었는데, 이 폴더 규칙에는 없어서 처음엔 놓쳤다.
- 재료의 iKAOS 프롬프트 템플릿 문서에 적힌 인라인 정답 표기 규칙("정답1=빈칸[1], 정답2=빈칸[2]")과
  팀이 실제로 시트에 기입하는 방식("정답1 한 칸에 쉼표로 구분해서 모두 적음")이 서로 달랐다.
  문서화된 템플릿 규칙이라고 해서 실제 운영 관례와 항상 같지는 않으므로, 애매하면 사람에게
  실제 사용 방식을 먼저 확인하는 게 안전하다. 또한 사용자가 "산출물"을 검토 중일 때 파일을
  덮어쓰려 하면 Excel 등에서 열려 있어 잠겨 있을 수 있다 — 그럴 땐 실패로 끝내지 말고 새 버전
  파일명으로 저장한다. **(2026-08-07 보강)** 이 항목이 단정한 "팀 관행 = 정답1에 쉼표로 합침"은
  이후 뒤집혔다 — 최종 확정값은 아래 "인라인 정답 표기 규칙이 …" 항목의 **정답1·정답2 분리**다.
  이 항목은 당시 경위 기록으로만 읽을 것.
- 검토자를 관점 다르게(누락/지어낸 값/SPEC 정합성) 3개 병렬 호출해보니, 단일 검토자 1회 실행보다
  더 많은 문제를 잡아냈다. 특히 "사람 확인 지점" 문구는 SPEC 원문을 그대로 복사하지 않고 제목+
  불릿으로 재구성했고, 위치도 파일 맨 아래가 아니라 중간(뒤에 문항 미리보기·CSV 안내 등이 더
  이어짐)이었다 — SPEC Step5 "결과물 맨 아래에 그대로 포함, 삭제·수정 금지"를 두 파일(v1.md,
  v2.md) 모두에서 어긴 상태다. 다음부터는 사람 확인 지점을 작성할 때 SPEC 문구를 그대로
  복사-붙여넣기하고 파일 맨 마지막 줄에 두며, 그 뒤에 다른 섹션을 추가하지 않는다.
- SPEC 4장에서 17번째 열 이름을 "정답해설"로 확정했는데도, 이후 만든 퀴즈생성_프롬프트_템플릿_v4.md와
  거기서 파생된 퀴즈결과_원고_1_v1.md 일부에 "정답피드백"/"정답 피드백"으로 다르게 표기된 채 남아있었다.
  새 버전 파일을 만들 때 SPEC의 확정 명칭을 다시 grep으로 대조하지 않고 손으로 옮겨 적어 생긴
  오타성 불일치로 보인다. 앞으로 열 이름처럼 SPEC에 확정값이 있는 항목은 복사-붙여넣기하고,
  검토자 호출 시 SPEC 정합성 관점을 포함시켜 이런 불일치를 잡는다.
- 자기검수 체크리스트를 10항목(PRD/SPEC 확정값)에서 11항목("단순 연도 암기 방지" 추가)으로
  늘렸는데, 그 변경을 PRD_요구사항정의서.md·SPEC_기능명세서.md에는 반영하지 않아 산출물과 기준
  문서가 서로 다른 숫자를 말하는 상태가 됐다. 산출물의 로직(체크리스트 항목 수 등)을 바꿀 때는
  같은 타이밍에 PRD/SPEC도 함께 갱신해서 "기준 문서 vs 실제 산출물" 불일치가 남지 않게 한다.
- CLAUDE.md 과제정의 표의 "사람이 확인할 것" 항목 중 "미발행 원고는 외부 도구에 원문 저장 금지
  (세션 내 사용만) 준수 여부"가 실제 산출물(v1.md·v2.md)의 "사람 확인 지점" 섹션에는 반영되지
  않았다. 사람 확인 지점을 작성할 때 SPEC Step5 문구뿐 아니라 CLAUDE.md 과제정의 표의 "사람이
  확인할 것" 행도 함께 체크리스트로 대조해야 빠뜨리지 않는다.
- HISTORY.md에 "템플릿·SPEC·산출물 모두 재반영했다"고 적어둔 변경이 실제로는 파일에 안 들어간
  사례가 두 건 발견됐다. (a) 인라인 보기를 "보기1·보기2 칸에 슬래시로 묶어 기입"으로 바꾼 변경이
  퀴즈생성_프롬프트_템플릿_v4.md에는 반영되지 않아, SPEC과 정반대인 낡은 규칙("보기1~3 = 빈칸[1],
  보기4~6 = 빈칸[2]")이 그대로 남아 있었다(HISTORY 17번 줄은 반영했다고 기록). (b) "정답피드백
  → 정답해설" 표기 통일도 템플릿 3곳(작성 규칙 제목, 17열 목록, 자기검수 10번)에 미반영 상태였다
  (HISTORY 30번 줄은 통일했다고 기록). 결과물이 틀리지 않은 건 퀴즈생성자가 템플릿과 SPEC을 함께
  읽었기 때문일 뿐, 템플릿만 보고 작업하면 틀리는 상태였다. 앞으로 "여러 파일에 반영"하는 변경은
  HISTORY에 기록하기 전에 파일별로 grep으로 반영 여부를 확인하고, 확인된 파일만 기록에 적는다.
- 인라인 정답 표기 규칙이 "정답1에 쉼표로 합치기" ↔ "정답1·정답2로 분리" 사이에서 **두 번 바뀌고
  한 번 재확인됐다** (HISTORY 14번 줄 쉼표 결합 → 19번 줄 분리 복귀 → 2026-08-06 분리 유지 재확인.
  세 번째는 논의만 있었고 규칙은 바뀌지 않았다). 2026-08-06 사용자 최종 확정: **정답 1칸에 정답 1개 —
  정답1 = 빈칸[1]의 정답 번호, 정답2 = 빈칸[2]의 정답 번호(분리)**. 보기는 보기1·보기2 칸에
  슬래시로 묶어 기입하는 방식과 함께 쓴다. 이 조합이 최종이며, 다시 바꾸자는 논의가 나오면
  문서 간 대조만 하지 말고 팀 시트에 실제로 기입된 예시부터 확인한다.
- 표기 하나를 정정할 때 "한 줄만 고치면 된다"고 판단·보고했는데, 검토자가 같은 문서 안에서 같은
  표기 4곳(SPEC 4장 107·118·119·129행의 `사지선다(단수)`류)을 더 찾아냈다. 원인은 문제를 발견한
  줄만 보고 같은 파일 전체를 grep하지 않은 것. 앞으로 표기·명칭을 정정할 때는 **수정 범위를 사용자
  에게 말하기 전에 해당 문자열을 프로젝트 전체 grep으로 세어보고**, "몇 개 파일 몇 곳"을 근거와
  함께 보고한다. 관련해서 (a) 산출물 파일이 스스로 "원본 + 변경사항 X만 반영한 버전"이라고 선언하고
  있으면(퀴즈생성_프롬프트_템플릿_v4.md 1·4행) 그 파일을 추가 수정할 때 변경사항 섹션도 함께
  갱신해야 선언이 거짓이 되지 않는다. (b) 기록에 "세 번 오갔다" 같은 횟수를 쓸 때는 실제 규칙이
  바뀐 횟수와 논의만 한 횟수를 구분한다 — 인라인 정답 표기는 규칙 변경 2회 + 재확인 1회이지
  변경 3회가 아니다.
- 산출물 문서에 "원본 + 변경사항 X만 반영했다"처럼 **자기 자신의 범위를 선언하는 문장**을 쓰면,
  그 선언 자체가 검증 대상이 된다. 퀴즈생성_프롬프트_템플릿_v4.md에 "이후 반영 사항" 섹션을
  추가해 선언을 고쳤는데도, 검토자가 v3 원본과 문장 단위로 대조해 기록되지 않은 차이 5건(역할
  문장 교체, 문장 4개 삭제, [입력 데이터] 블록 위치 이동, 설계 원리 섹션 재작성)을 더 찾아냈다.
  또 "표기를 통일했다"고 쓴 범위가 실제보다 넓었다(고정 배열·17열 목록만 통일했는데 전부 통일한
  것처럼 읽혔다). 앞으로 (a) 범위를 선언하는 문장은 **원본과 실제로 diff를 떠서 확인한 뒤에만**
  쓰고, (b) "통일했다/전부 반영했다" 같은 표현은 적용 범위를 괄호로 함께 적는다.
- CSV를 근거로 "몇 행"이라고 인용할 때, 셀 안에 줄바꿈이 있으면 **텍스트 파일의 줄 번호와 Excel의
  행 번호가 달라진다**. Story전체 목차_0730.csv는 줄바꿈이 11곳 있어 파일 141줄 = 레코드 130개다.
  대시보드에 "목차 10행"이라고 적었더니 Excel에서는 8행을 가리키는 상태가 됐다. 사람이 열어볼
  산출물에는 행 번호 대신 **값 자체**(분과/중단원/아티클명)를 근거로 적는다.
- 두 문서가 **같은 숫자를 쓰는데 뜻이 달라서** 불일치가 오래 숨어 있었다. SPEC·에이전트 정의는
  자기검수를 "11개 = 원본 10개 + 분과 가이드"로, 템플릿 체크리스트는 "11개 = 원본 10개 + 연도
  암기"로 적어 **서로 다른 항목을 11번이라 불렀다.** 둘 다 "11항목"이라 적혀 있으니 grep으로
  숫자만 맞춰봐서는 어긋난 걸 알 수 없었고, 실제 점검 항목은 12개인데 PRD는 아직 10개였다.
  2026-08-07에 12개로 확정하고 번호(11=연도 암기, 12=분과 가이드)를 SPEC에 못박았다. 앞으로
  체크리스트·목록의 개수를 문서에 적을 때는 **숫자만 쓰지 말고 항목 이름까지 함께 적어**,
  숫자가 같아도 내용이 다른 상태를 잡을 수 있게 한다.
- **브라우저는 로컬 프로그램을 실행할 수 없다.** 대시보드에서 "클릭하면 엑셀로 원본 열기"를 만들려고
  상대경로 링크 → 다운로드(사본 생성) 문제를 겪고, Office의 `ms-excel:ofe|u|` 프로토콜로 바꿨더니
  엑셀만 뜨고 파일은 열리지 않았다. 원인은 레지스트리에 등록된 핸들러가 `protocolhandler.exe`로,
  SharePoint·OneDrive 같은 **웹 URL 전용**이라 로컬 경로를 처리하지 않기 때문이다. 결론: 로컬
  HTML에서 로컬 파일을 앱으로 여는 건 링크로 해결되지 않는다. **전체 경로를 클립보드에 복사**해
  Excel 열기 창·탐색기 주소창에 붙여넣는 방식이 유일하게 확실하다. 앞으로 "클릭 한 번에 로컬 앱
  실행"류 요구가 나오면 먼저 이 제약을 설명하고 대안을 제시한다. 덧붙여, 경로 같은 환경 의존 값은
  파일 곳곳에 박지 말고 `BASE` 상수 한 곳에 모아 폴더 이동에 대비한다.
- **"표시용 라벨"이라고 생각한 곳에서 값을 지어냈다.** 대시보드·미리보기에서 대단원명을
  `1. 빅뱅: 우주의 시작`처럼 **콜론**으로 적었는데, 원본(`재료/Story전체 목차_0730.csv`, 최종 원고
  머리말)은 전부 **엠대시** `1. 빅뱅 — 우주의 시작`이었다. 재료 전체에 콜론 표기는 0건이었다.
  게다가 이 값이 미리보기의 "엑셀 반영 요청서"에 실려 나가도록 되어 있어, 표시용이 아니라 실제
  데이터로 흘러갈 수 있는 상태였다. 또 검수자 이름 입력칸 placeholder에 실명형 이름을 예시로
  지어 넣었다. 교훈: **화면에 보이는 고유명사는 전부 원본에서 복사**하고, 구분자(—, :, ·)까지
  바꾸지 않는다. 예시 placeholder에는 사람 이름 같은 고유명사를 만들어 넣지 않는다.
- **세어보지 않은 숫자를 근거처럼 적었다.** 미리보기의 "검수 정보"에 발문 74자·카드 44~48자·보기
  26~48자라고 써 놓았는데, 검토자가 실제로 세어보니 93자·43~50자·29~60자였다. 서브에이전트가 보고한
  값을 그대로 옮겨 적었고 직접 검증하지 않은 것이 원인이다. 숫자는 "지어낸 값"으로 취급되므로,
  **글자 수·개수·비율처럼 검증 가능한 수치는 반드시 직접 세어 확인한 뒤 적는다.** 다른 에이전트가

  옛 규칙이 새 규칙을 이기는** 상태가 될 뻔했다(검토자가 발견). 앞으로 규칙을 바꿀 때는 ① 유형별 절
  ② 공통 원칙 ③ **상위 요약·최우선 절** ④ 자기검수 항목 네 곳을 세트로 확인한다. 상위 요약 절은
  본문을 요약한 것이므로 **본문만 고치면 반드시 어긋난다.**
- **"어디에 반영했다"고 적기 전에 그 파일을 열어 확인한다.** 같은 날 SPEC과 진행상황에 A/B 키워드
  차별화를 **"자기검수 4번에 반영"**이라고 적었는데, 정작 4번 원문이 있는 v5에는 한 글자도 넣지
  않았다. 부속 문서(`퀴즈_AB_2안_생성기준.md`)에만 넣고 반영했다고 기록한 것이다. 검토자 세 명 중
  둘이 같은 지점을 잡았다. **반영 위치를 문서에 명시할 때는 그 위치를 grep으로 확인하고 적는다.**
- **예시를 들 때 그 예시가 원고에 실재하는지 확인한다.** 비유 금지 규칙을 쓰면서 `결합 손`의 대체
  용어로 "원고에 함께 나오는 정식 용어(`공유 결합`·`원자가 전자`)"라고 적었는데, **`원자가 전자`는
  `결합 손`이 나오는 두 원고 어디에도 없었다**(검토자가 원고를 열어 확인). "지어내지 말라"는 규칙을
  쓰면서 그 문장 안에서 지어낸 셈이다. 대체어 목록을 없애고 "같은 원고 안에서 그 개념을 가리키는
  정식 용어를 찾아 쓰라"는 지시로 바꿨다. **규칙 문서의 예시도 재료 대조 대상이다.**
- **사용자 지침을 옮길 때 없던 우선순위·조건·수치를 붙이지 않는다.** 사용자는 A/B를 "서로 다른 핵심
  키워드**나** 학습 포인트로" 구성하라고 **병렬**로 말했는데, 문서에는 "1순위는 핵심 키워드", "키워드가
  둘 이상이면 → 키워드로, 하나뿐이면 → 학습 포인트로"라는 **순위와 조건 분기**가 붙었다. "어느 쪽을
  골라도 학습 가치가 같아야 한다", "넷이나 나오는 경우는 드물다" 같은 근거 없는 요건·빈도 주장도
  들어갔다. 2026-08-12에 글자 수 "60자/80자"를 임의로 붙였다가 폐기한 것과 **같은 종류의 실수**다.
  옮겨 적을 때는 **사용자 문장의 접속사(나/또는 ↔ 먼저/그다음)와 강도(가능한 한 ↔ 반드시)를 그대로
  유지**하고, 판단 기준을 새로 만들지 않는다.
- **"문서에 규칙이 있다"와 "구현이 그 규칙을 지킨다"는 다른 문제다.** 2026-08-15에 "직접 입력 채점은
  공백을 무시한다"를 확정하고 SPEC·템플릿·에이전트 정의에 전부 반영했는데, **미리보기의 채점 코드는
  입력값만 공백을 지우고 정답은 그대로 비교하고 있었다.** 그래서 `정역학적 평형`처럼 띄어 쓴 정답이
  13일 동안 전부 오답 처리되고 있었고, 사용자가 같은 규칙을 다시 알려줄 때까지 아무도 몰랐다.
  규칙이 **채점·표시 같은 동작에 관한 것이면 문서만 고치지 말고 그 동작을 실제로 한 번 돌려서 확인**한다
  (정답을 띄어 써 넣어 보기 / 예문 없는 문항 화면 보기 수준으로 충분했다).
- **데이터가 `-`로 자리를 지키는 규칙과, 그것을 화면에 보여주는 것은 별개다.** 예문 없는 칸에 `-`를
  넣는 규칙(`X` 금지 — OX 정답과 혼동)은 **17열 데이터의 규칙**인데, 템플릿이 `if (item.ex)`로만 검사해
  `-` 한 글자가 든 빈 지문 박스를 그리고 있었다. **"빈 값을 표현하는 문자"는 저장용이고, 표시할 때는
  빈 값으로 취급**해야 한다. 앞으로 `-`·`N/A` 같은 자리 지킴 문자를 도입하면 표시 코드도 함께 본다.
- **표기 기호를 정할 때 그 프로젝트에서 이미 쓰는 기호와 겹치는지 본다.** 순서배열 카드 라벨로
  A·B·C·D가 자연스러워 보였지만, 이 과제는 **A안·B안**으로 14문항을 관리해서 "4A의 정답은 B-D-A-C"처럼
  안(案) 기호와 카드 라벨이 한 문장에 섞인다. `가`·`나`·`다`·`라`로 정해 충돌을 없앴다. 기호를 새로
  도입할 때는 **기존 기호 목록과 대조**한다.
- **표시 형식이 바뀌어도 데이터 구조는 안 바꾸는 쪽이 싸다.** 카드 라벨을 숫자에서 `가`·`나`·`다`·`라`로
  바꿀 때 JSON의 `order.ans`를 라벨 문자열로 옮길 수도 있었지만, **숫자 배열로 두고 화면에서 변환**하게
  했다. 덕분에 이미 만든 5건을 다시 만들지 않았고 검증 스크립트도 그대로 쓸 수 있었다. 바꿔야 하는 것이
  **표시**인지 **저장**인지 먼저 가른다.
- **사람이 손으로 옮겨 적는 단계가 파이프라인에 있으면 검사 도구를 붙인다.** `퀴즈생성자`는 Write 권한이
  없어 결과를 사람이 JSON으로 옮겨 담는데, **정답 번호 하나만 틀려도 미리보기가 틀린 답을 정답으로
  표시**한다. `산출물/도구/퀴즈JSON검증.js`를 만들어 저장 직후 돌리게 했다. 다만 이 검사는 **구조와 자기
  일관성만** 본다 — 정답이 원고에 맞는지는 여전히 사람이 미리보기에서 확인해야 한다.
- **한국어 낱말을 일괄 치환할 때는 조사와 단위 명사를 함께 본다.** '카드'(모음 끝) → '문장'(자음 끝)으로
  94군데를 바꾸자 `문장는`·`문장를`·`문장가`·`문장로`가 68군데 생겼고, `카드 문장의 용어를` → `문장 문장의
  용어를` 같은 **중복 낱말**과 `카드 4장`(→ `문장 4개`) 같은 **단위 명사** 문제도 나왔다. 게다가 마크다운
  강조가 조사 사이에 끼어(`문장**가`) 단순 문자열 치환으로는 잡히지 않는 것이 2군데 있었다.
  절차: ① 어색해지는 문구를 **먼저 문구째로** 바꾼다 ② 단위 명사를 정규식으로 바꾼다 ③ 낱말을 치환한다
  ④ **조사 교정**(는→은, 를→을, 가→이, 로→으로, 와→과)을 강조·코드 표시를 허용하는 정규식으로 돌린다
  ⑤ 바뀐 문단을 **눈으로 한 번 읽는다.** ⑤를 건너뛰면 문법이 깨진 프롬프트를 에이전트에게 주게 된다.
- **학습자가 읽는 말과 구현상의 이름을 구분한다.** 순서배열 항목을 코드에서는 `ocard`, 문서에서는 '카드'로
  불렀는데 그 말이 **발문에까지 흘러 들어가** 학습자 화면에 노출됐다. 사용자가 '문장'으로 바로잡았다.
  UI 구현 용어를 규칙 문서에 쓰면 발문에 그대로 새어 나가므로, **발문에 쓸 말을 규칙에 명시**하고
  구현 용어는 코드 안에만 둔다. 발문 표기만 고치면 규칙 본문을 보고 되돌아가므로 **어휘를 한쪽으로 모은다.**
- **"고쳤다"는 기록이 그 코드가 파일에 있다는 증거는 아니다.** HISTORY에는 미리보기 템플릿에
  `ORD_LABEL`·`ordLabel()`·`ordAnsText()`를 넣었다고 적혀 있었지만 **실제 파일에는 호출부만 있고 정의가
  없었다.** 그 상태로 미리보기 5건이 생성되어, 순서배열 문항에서 ReferenceError로 화면이 아예 그려지지
  않았다. 규칙 문서(v5·SPEC·CLAUDE.md)는 전부 맞게 고쳐져 있었기 때문에 **문서만 대조하면 통과로 보인다.**
  절차: 규칙을 바꿨으면 ① 문서 ② **그 규칙을 실행하는 코드** ③ **이미 만들어 둔 산출물** 세 곳을 각각
  확인하고, 기록에 "넣었다"고 쓰기 전에 `grep`으로 정의가 있는지 본다.
- **검사 도구가 보지 않는 층이 어디인지 알고 있어야 한다.** `퀴즈JSON검증.js`는 JSON 구조만 보므로 화면
  전용 함수가 통째로 사라져도 **"전항목 통과"가 나온다.** 반대로 화면이 라벨로 바꿔 보여주는 값(검수
  정보의 `정답 1`)은 JSON 문자열이라 검증기가 볼 수 있는데도 검사 항목이 없어 20건이 옛 숫자 표기로
  남아 있었다. 표시 규칙을 바꿀 때는 **그 규칙을 지키는지 확인해 줄 도구가 있는지**를 함께 정하고,
  없으면 그 자리에서 만든다 — 이번에는 생성기에 "템플릿에 함수 정의가 없으면 중단"을, 검증기에
  "`정답 1`이 `ans`의 라벨 형식과 같은가"를 넣었다.
- **가드를 넣었으면 일부러 깨뜨려 걸리는지 본다.** 새로 넣은 검사 2개를 각각 고장 낸 사본으로 돌려
  실제로 중단·불일치가 나는 것을 확인한 뒤 원상복구했다(md5로 복구 확인). 통과만 보고 끝내면 **검사가
  실제로는 아무것도 안 하는 상태**를 알아채지 못한다.
- **표기 규칙을 바꿀 때는 "표기"와 "채점"을 분리해서 말한다.** 빈칸 표기를 `_`로 바꾸며 띄어쓰기를
  살렸지만 **채점은 여전히 공백을 무시**한다. 두 가지를 한 문장에 뭉쳐 쓰면 "띄어쓰기를 반영한다"가
  채점까지 엄격해진다는 뜻으로 읽힌다. 규칙 문서 6곳에 **"표기가 띄어쓰기를 보여주는 것과 채점이 공백을
  무시하는 것은 별개"**를 같이 적었다.
- **표기 문자를 바꾸면 그 문자를 잡던 정규식·CSS도 같이 본다.** `○`는 한 덩어리(`/○+/g`)로 잡히지만
  밑줄 표기는 **사이에 공백이 들어가서** 같은 방식으로는 `__ ____ __`가 세 조각으로 쪼개진다.
  `/_+(?: _+)*/g`로 바꾸고, 줄바꿈으로 끊기지 않게 `white-space:nowrap`도 함께 넣었다. 표기를 바꿀 때는
  ① 규칙 문서 ② 그 표기를 만드는 쪽 ③ **그 표기를 읽는 쪽(정규식·검증기·CSS)** 을 한 묶음으로 고친다.
- **현황판을 갱신할 때 표만 고치고 산문 문장을 놓친다.** 2026-09-01 별 반영 후 `진행상황.md`의 표
  수치(4건 → 5건, 대기 1건 → 0건)는 고쳤는데, 같은 파일의 산문 서술 세 곳이 어제 기준으로 남았다 —
  0-1장 "사람 선택 대기 상태다", 5장 "CSV 반영은 24건 전부 대기 상태다 — 빈 스켈레톤이다", 그리고
  "2026-08-31에 4개 아티클이 채워졌다". **표와 본문이 정면으로 충돌하는 파일**이 되어, 다음 세션이
  어느 쪽을 믿을지 알 수 없다. 절차: 숫자를 고쳤으면 그 숫자가 **문장으로도 적혀 있는 자리**를
  `grep`으로 찾아 함께 고친다(예: `grep -n "대기\|스켈레톤\|4개\|4건"`). 표만 고치는 것은 갱신이 아니다.
- **간섭 쌍은 "앞 건에 적었으면 이번 건에도 적는다".** 앞 4건은 「동시 선택 시 정답이 노출되는 쌍」을
  기록했는데 별 1건만 빠졌다. 실제로 별 확정 선택에는 `3A+7B`(7B 보기4 = 3A 정답)와 `1B+6A`(1B 예문이
  6A 정답 보기 2개를 알려줌) 두 쌍이 들어 있었다. 규칙 위반은 아니고 사람이 고른 것이라 반영은 그대로
  하지만, **적지 않으면 다음에 같은 조합을 권할 때 근거가 사라진다.** 반영 직후 선택 7개를 서로
  대조해 간섭 여부를 한 번 훑고, 없으면 "없음"이라고 적는다.
- **세는 값은 세어 보고 적는다.** 서브에이전트가 "예문 없는 6문항은 `-`를 유지했다"고 기록했으나 실제로는
  5문항이었다(1번 인라인과 5번 직접 입력에는 예문이 있다). 7에서 2를 빼는 자명한 계산이라 검토 없이는
  넘어간다. **개수를 적을 때는 어느 항목인지 함께 적는다** — "5문항(2·3·4·6·7번)"처럼 쓰면 세지 않고는
  쓸 수 없어 틀린 수가 남지 않는다.
- **"권장"을 문서에 넣을 때는 "필수"와 섞이지 않게 층을 분리한다.** 2026-09-01에 모범 문항 지향

  만들지마가 아니라, 되도록 이렇게 만들어줘. 이렇게 못 만드는 문제는 기존 출제대로 만들면 됨"**이라고
  바로잡았다(원문 그대로). 필수로 넣었다면 원고 조건상 그
  형태를 못 만드는 문항이 전부 **미통과**가 되어 생성이 막히거나, 통과시키려고 소재를 비트는 —
  규칙 3번(지어내지 않는다) 위반이 유도됐을 것이다. 방법: ① 마크를 다르게 준다(`★` 필수 / `☆` 지향)
  ② 판정 어휘를 다르게 준다(`통과`/`미통과` vs `달성`/`해당 없음`/`미달성 — 사유`) ③ 항목 수를 늘리지

  절차: 산출물이 **런타임에 만들어지는 것인지 파일에 박혀 있는 것인지** 먼저 구분하고, 런타임 생성물은
  **생성 로직(판정식) 자체를 읽어** 검증한다. 개수를 세는 검증은 파일에 박힌 값에만 쓴다.

  애초에 넣을 자리가 없었다. 총괄 문장을 쓸 때는 **예외를 그 자리에 함께 적는다** — "1~8번은 …,
  9번은 …가 구현하고 …가 확인한다"처럼. 그리고 일부러 뺀 항목에는 **"여기에 추가하지 마라"**를
  대상 문서에 적어 둔다. 그러지 않으면 다음 세션이 "빠졌다"고 보고 채워 넣는다.
- **확정·CSV 반영이 끝난 뒤에도 원고는 바뀐다 — 문항은 "완료"가 아니라 "그 판 원고에 대한 완료"다.**

  날짜만 비교하면 되고 비용이 거의 없다 ② 원고가 바뀌면 **그 아티클의 확정 문항 전체를 재판정**한다
  (이번엔 7문항 중 무영향 4·경미 1·검토 1·수정 1이었다) ③ **전체 재생성으로 도망가지 않는다** —

  아꼈고, 멀쩡한 6문항과 모범 문제 2건을 그대로 지켰다.
- **한 칸만 고칠 때는 "한 줄만 바뀌었는가"를 기계로 확인한다.** CSV 한 칸을 문자열 치환으로 고치기 전에
  **그 문자열이 파일 안에서 유일한지 세고**(1건 확인), 고친 뒤 **줄 단위 diff로 달라진 줄이 정확히
  하나인지** 확인했다(파일 27행). 열 수·BOM·줄 수도 함께 봤다. 눈으로 보면 통과처럼 보이는 수정에서
  다른 줄이 함께 망가지는 사고가 이 프로젝트에 이미 2회 있었다.

  예외를 던지고 멈췄지만, **아무도 그 콘솔 메시지를 보지 않았고 HTML은 옛 내용 그대로 남아 있었다.**
  → 집계 폴더에는 집계 대상만 둔다. 도구가 폴더를 통째로 읽는다면 **대상 파일을 이름 규칙으로
  좁히고(예: 두 자리 번호로 시작), 규칙 밖 파일은 멈추지 말고 제외하고 알린다.** 그리고 자동 생성

  그건 통과가 아니라 **검사가 없는 상태**임을 뜻한다.

**무엇이 왜 발생했나.** `B. 과학 연구의 목표` 7B 순서배열 네 문장에 `원소를 성질의 규칙성에 따라

그 연도가 실린 칸을 함께 밝힌다**(보기 N / 해설). 해설이라고 적히면 그 자체가 미통과 신호다.

## 2026-09-17 · 순서배열에서 **동시적 상관**을 순서로 쓰면 안 된다 (하루에 두 번 걸렸다)

**무엇이 왜 발생했나.** 규칙 4번 ②("이론적으로 순서가 필연적")를 만족한다고 보고된 순서배열 두 벌이
실제로는 **앞뒤가 동시에 성립하는 진술**이었다.
- `B. 별의 관측` 7번: `질량이 크면 광도·온도가 높다` ↔ `광도·온도가 높은 별은 H-R도 위쪽에 있다`.
  둘은 같은 사실의 두 면이라 뒤바꿔도 각각 참이다.
- `A. 별의 진화` 4번: `외피가 흩어져 행성상 성운을 이룬다` ↔ `중심에 백색왜성이 남는다`.
  **원고 13행이 이 둘을 한 문장 안에서 `~남기고, 가운데에는 ~남습니다`로 동시에 서술**하고 있었다.

**핵심 구분.** 규칙 4번 ②가 요구하는 것은 **"앞 문장이 뒤 문장의 성립 조건"**이다.
`A → B`가 참이어도 `A`와 `B`가 **같은 시점의 두 서술**이면 순서 근거가 아니다.
2026-09-11의 "개념적 전제 관계 ≠ 사건의 순서"와 같은 계열이고, 이번에는 **상관 관계 ≠ 순서**다.

**재발 방지.** ① 자기검수 15번에서 인접 쌍마다 **"앞이 없으면 뒤가 성립하지 않는다"를 한 문장으로 써 본다.**
"앞이 먼저 일어난다"가 아니라 **"앞이 없으면 뒤가 말이 안 된다"**여야 통과다.
② **원고에서 두 문장이 한 문장 안에 묶여 서술되어 있으면 동시로 의심한다** — 이번 `A. 별의 진화`가
그 신호를 그대로 보여 줬다. 원고 문장 경계를 먼저 본다.
③ 동시로 판명되면 **둘을 하나로 합치고 빈자리에 앞 단계나 뒤 단계를 넣는다.** 이번에는 각각
`관측 단계`(별의 관측)와 `식어 가는 단계`(별의 진화)를 원고에서 찾아 채웠다. 소재를 지어내지 않는다.

## 2026-09-17 · 규칙 검사는 **사전(dictionary)이 패턴보다 낫다** — 한국어 인명에서는 특히

**무엇이 왜 발생했나.** 규칙 10번(보기 칸에 과학자 풀네임 금지)을 기계로 잡으려고

  어절과 일반 명사·어미는 형태로 구분되지 않는다.

| **동시적 상관** | `공급된 에너지가 결정 구조를 무너뜨린다` ↔ `온도가 0도에 머문다` | 두 문장이 **같은 시간 구간**을 가리킨다. 한쪽은 관찰, 한쪽은 그 이유. 원고가 "왜 그럴까요? ~ 때문입니다"로 쓰고 있으면 거의 이 경우다 |
| **논리적 동치의 재진술** | `물리적 방법으로는 갈라지지 않는다` ↔ `화학 반응이 필요하다` | "A ⇔ not-B"라서 **뒤바꿔도 둘 다 참**이다. 원고가 두 문장을 **붙여서** 썼으면 의심한다 |
| **개념적 전제** | VSEPR 일반 원리 ↔ 비공유 전자쌍이 넓은 자리를 차지한다 | 한쪽이 **모든 경우에 적용되는 일반 원리·정의**다. 사건이 아니라 성질 서술이면 단계로 쓸 수 없다 |

**왜 생겼나.** 자기검수 15번을 "앞이 없으면 뒤가 불가"만 확인하고 끝냈기 때문이다. 세 경우 모두
그 문장은 참이지만, **역방향도 같이 참**이어서 순서가 정해지지 않는다.

**재발 방지.**
1. **양방향으로 따진다.** "앞이 없으면 뒤가 불가"가 성립해도, **"뒤가 없으면 앞이 불가"까지 성립하면
   그 쌍은 순서가 아니다.** 한 방향으로만 성립해야 한다. 이 문장을 자기검수 15번에 쌍마다 적는다.
2. **각 문장이 사건인지 본다.** 일반 원리·정의·독립된 성질 서술은 단계가 아니다. 네 문장의 **층위가
   서로 달라야** 한다(상태 / 조작 / 반응 / 생성물처럼).
3. **가장 안전한 형태는 「앞 단계의 산물이 뒤 단계의 재료가 되는」 사슬이다.** 뒤바꾸면 재료 자체가
   없어지므로 동치가 될 수 없다. 이번에 채택된 세 벌이 전부 이 형태다(분자→원자→전자·이온 /
   혼합물→정제수→성분 원소 / 현상→반증→결론→정식화).
4. 원고에 그런 사슬이 없으면 **억지로 만들지 말고 15번 미통과로 보고한다.** 다만 **유형까지 바꾸지는
   않는다** — 이번에 생성자가 7번을 사지선다로 바꿔 와 검증기가 고정 배열 오류 2건을 냈다.
   순서배열 자리는 **다른 소재로 순서배열을 만들거나, 다른 자리와 소재를 맞바꾸는** 것으로 푼다.

**부수 소득.** 소재를 맞바꾸자 따로 있던 정답 노출 위험도 함께 사라졌다(`B. 물질의 상태`의 4번 보기가
5번 정답 `잠열`의 정의였던 문제). 순서배열 소재를 옮길 때 **노출 쌍도 같이 풀리는지** 확인하면 이득이다.

## 2026-09-18(2) — 원고가 «한 문장»에 묶어 쓴 두 내용은 순서배열 두 단계로 쪼개지 않는다

   (2026-09-18 첫 항목의 "층위가 서로 달라야 한다"와 같은 이야기다).
2. **표현을 행위형으로 바꿔 쓰는 것으로는 동시성이 해소되지 않는다.** 바꿔 쓰기 전에 **원고에서 그 행위가
   별개 문장으로 서술되어 있는지**부터 본다. 없으면 그 소재를 쓰지 않는다.
3. **성질 서술(정적 사실)을 사슬의 출발점으로 두면 늘 개념적 전제 의심을 받는다.** 원고가 그 자리에

## 2026-09-18(3) — 순서배열이 걸리는 «네 번째 얼굴»: 명명·역사적 선후 / 그리고 이론사 사슬의 함정

3. 인접 쌍마다 **"이 둘은 다른 곳에서 일어나는가, 다른 시각에 일어나는가"**를 묻는다. 둘 다 아니면 동시적이다.

3. **화학 원고에서 안전한 사슬은 「물질이 바뀌어 다음 반응의 재료가 되는」 것 하나다.** 이번에 통과한 것은

   "쪼개지 않고 합쳤다"고 보고한 말을 그대로 받아들인 것이 원인이다. **원고 문장을 옆에 놓고 보기 4개와
   글자 단위로 맞춰 봐야 한다** — 생성자의 "합쳤다"는 말은 어느 경계에서 합쳤는지를 말해 주지 않는다.

두 단계를 뽑아내면 거의 이 함정에 빠진다.**

**재발 방지**: 순서배열 4문장을 낸 뒤 **각 문장이 원고의 어느 문장에서 왔는지 적어 본다.
인접한 두 문장이 원고의 같은 한 문장에서 나왔으면 그 고리를 의심한다.** 이어서 2026-09-21의
검사("두 문장을 맞바꿔도 말이 되는가")와 함께 돌린다. 판정 문구는 그대로
**"앞이 없으면 뒤가 말이 안 된다"**이며, `가`의 「응결로 방출된」처럼 **뒤 문장이 앞 문장을 수식어로
다시 품고 있으면** 새 사건이 아니라 같은 사건의 재서술일 가능성이 높다.

`06_지구_D_해양생명과생태계.json`의 `meta.행`이 `"[확인 필요 — 대단원누적자가 스켈레톤 행 확인]"`
